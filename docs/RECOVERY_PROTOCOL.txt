IMPORTANT — LONG-RUNNING TASK / USAGE-LIMIT RECOVERY PROTOCOL

This project may take longer than my available Codex usage window. You must therefore make the entire development process safely resumable.

Follow these rules throughout the project:

1. NEVER keep important progress only in your conversation context.

2. Work incrementally. After every meaningful milestone, save all changes to disk.

3. Maintain a persistent file in the project root named:

   CODEX_PROGRESS.md

This file is the authoritative recovery checkpoint for the project.

4. Continuously update CODEX_PROGRESS.md with:

   - Overall project goal
   - Original requirements
   - Architecture being used
   - Technology stack
   - Completed milestones
   - Current milestone
   - Exact task currently being performed
   - Files created
   - Files modified
   - Important implementation decisions
   - Database changes
   - API endpoints completed
   - Frontend pages/components completed
   - Backend modules completed
   - Dependencies installed
   - Environment variables required
   - Credentials/API keys that I still need to provide manually
   - Tests already executed
   - Tests that passed
   - Tests that failed
   - Known bugs
   - Remaining tasks
   - Exact next action to perform when work resumes

5. Also maintain:

   TODO.md

Use it as a structured checklist containing every remaining project task.

Mark items using:

   [x] Completed
   [ ] Not completed
   [~] In progress

6. Before starting any significant task, update CODEX_PROGRESS.md with:

   CURRENT TASK:
   <description>

   CURRENT FILES:
   <files being modified>

   NEXT STEP:
   <exact next operation>

7. After completing the task, update the checkpoint again.

Therefore, if execution stops unexpectedly, the maximum lost work should be very small.

8. Use Git throughout development.

After every stable milestone:

   git add .
   git commit -m "checkpoint: <short description of completed work>"

Do NOT commit secrets, API keys, passwords, .env files, tokens, generated build directories, or other sensitive information.

Ensure .gitignore is configured correctly before committing.

9. Make commits small enough that development can safely resume from the latest commit.

10. If you detect that available execution/context/usage is getting low, STOP starting large new operations.

Instead:

   a. Finish the smallest safe unit currently being worked on.
   b. Save all files.
   c. Run any relevant quick verification.
   d. Update CODEX_PROGRESS.md.
   e. Update TODO.md.
   f. Commit the stable state to Git.

Then write a section in CODEX_PROGRESS.md named:

   ## RESUME POINT

It must contain:

   LAST COMPLETED TASK:
   ...

   CURRENT PROJECT STATE:
   ...

   CURRENTLY IMPLEMENTING:
   ...

   EXACT NEXT STEP:
   ...

   NEXT FILE TO OPEN:
   ...

   NEXT COMMAND TO RUN:
   ...

   REMAINING ISSUES:
   ...

12. Never repeat completed work unless verification shows that it is broken.

   b. Read CODEX_PROGRESS.md completely.
   c. Read TODO.md completely.
   d. Check git status.
   e. Inspect recent commits using git log.
   f. Check the current implementation.
   g. Verify that the files mentioned in the RESUME POINT exist.
   h. Determine exactly where execution stopped.

Then continue directly from:

   ## RESUME POINT
